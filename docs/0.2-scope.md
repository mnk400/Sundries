# Sundries 0.2 — Adapter Shapes

The goal of 0.2 is **not a new integration**. It is to get the interfaces into a shape where adding one is a
couple of classes and no UI code — so that Jira, SIM, Reminders and Linear can land later without a round of
core-model surgery each.

Deliberately shipped before the integrations, and deliberately after 0.1's test suite: this release moves the
Markdown adapter's foundations underneath it, and the 44 tests are what make that safe.

**Behaviour should not change.** Markdown comes out the other side rendering, parsing and writing exactly as it
does today. If a user notices 0.2 happened, something went wrong.

---

## The principle

> Fields Sundries itself **reasons about** stay first-class and typed. Everything else is a bag.

The store sorts by due date, counts overdue, and toggles completion — so `title`, `dueDate` and `isCompleted`
remain real properties of `TaskItem`. Priority, sprint and story points are things Sundries only ever displays
or hands back to the source, so they live in a keyed collection that no core file enumerates.

Getting greedy and pushing due date into the bag too would mean `TaskStore` parsing its own metadata to compute
a menu-bar count. Getting timid and promoting priority to a real property means every new service edits
`TaskItem`.

And the rule that makes the whole thing work, stated once:

> **Field *meanings* are open. Field *value types* are closed.**

What a field *means* (`due-date`, `location`, `story-points`) is a namespaced string that no core file lists.
What a field *contains* is one of a small closed set the UI can exhaustively switch over. Story points renders
as a stepper not because Sundries knows what a story point is, but because the adapter said `.number`. A
recognised meaning only ever *upgrades* a field to a nicer editor; it is never required for one to work.

## 1. The field model

New types. None of this exists today.

```swift
struct TaskFieldID: Hashable, Sendable, ExpressibleByStringLiteral { let rawValue: String }
// Known IDs are conveniences, never a closed set:
extension TaskFieldID { static let dueDate: Self = "due-date" }

enum TaskFieldValue: Hashable, Sendable {   // closed — the editor registry switches over this
    case text(String)
    case number(Double)
    case date(Date, includesTime: Bool)
    case flag(Bool)
    case choice(String?)        // TaskFieldOption.id
    case choices([String])
}

struct TaskFieldOption: Identifiable, Hashable, Sendable {
    let id: String
    let displayName: String
    let detail: String?
    let symbolName: String?
}

struct TaskField: Identifiable, Sendable {
    let id: TaskFieldID
    let displayName: String            // chip label
    let symbolName: String
    let kind: Kind                     // text / number / date / flag / choice / multiChoice
    let isRequired: Bool
    let optionsAreDynamic: Bool        // ask the adapter rather than using baked-in options
    let invalidatedBy: [TaskFieldID]   // "sprint options change when project changes"
}
```

- [ ] `TaskFieldID`, `TaskFieldValue`, `TaskFieldOption`, `TaskField`, `TaskFieldIssue`
- [ ] `TaskDraft` gains `var fields: [TaskFieldID: TaskFieldValue]`; `dueDate` becomes a computed accessor over
      `fields[.dueDate]` so existing call sites keep reading naturally
- [ ] `TaskItem` gains the same bag for display

**Options are a provider, not an array.** A choice field cannot carry `[TaskFieldOption]` baked in at schema
time: Jira's sprint list depends on the selected project, priorities come off the network, and a project list is
long enough to want search. Markdown uses none of this; Jira needs all of it on day one, which is exactly why it
belongs in the shape work rather than the integration work.

## 2. The adapter protocol

`Services/TaskSourceAdapter.swift` is 12 lines and four methods today.

```swift
protocol TaskSourceAdapter: Sendable {
    var descriptor: TaskSourceDescriptor { get }
    func fetchTasks() async throws -> [TaskItem]
    func fetchDestinations() async throws -> [TaskDestination]

    // new — every one of these gets a default implementation
    func composerSchema(for destination: TaskDestination) async throws -> [TaskField]
    func options(for field: TaskFieldID, in draft: TaskDraft) async throws -> [TaskFieldOption]
    func validate(_ draft: TaskDraft, for destination: TaskDestination) -> [TaskFieldIssue]

    func createTask(_ draft: TaskDraft, in destination: TaskDestination) async throws -> TaskItem
    func setCompleted(_ task: TaskItem, isCompleted: Bool) async throws
}
```

- [ ] Default implementations in a protocol extension — the default schema is `[dueDate]`, no dynamic options,
      no validation issues. `MarkdownTaskSource` should implement **none** of the three new methods.

**`composerSchema` takes the destination even though Markdown ignores it.** This is the single most
expensive-to-retrofit decision in the release. In Jira the project and issue type determine which fields exist
and which are mandatory — a Bug and an Epic in one project do not take the same form. If the schema were a
static `var`, making it destination-dependent later would mean rewriting the composer's state model, because
selecting a destination has to be able to invalidate field state mid-compose. Adding the argument now costs one
unused parameter.

Destination therefore stops being a peer field and becomes **the routing key that resolves the rest of the
schema**.

## 3. The composer

`Views/MenuBarContentView.swift` is where the hardcoding lives, and also where the good news is.

`DrawerContentHost` (`Views/DrawerMotion.swift:78-107`) makes **no height assumptions at all** — it is a `ZStack`
that renders `content(route)`, clips it, and animates the transition. `DrawerState` is already generic over
`Route: Hashable`. The expensive animation machinery survives this release untouched; only the route token
becomes data.

- [ ] `ComposerPanel` (`:198-201`) — private enum of `.date`/`.destination` — becomes `TaskFieldID`
- [ ] The two hand-placed chips (`:221-286`) become `ForEach` over the schema
- [ ] The drawer's `switch` (`:292-312`) becomes an **editor registry**
- [ ] `.disabled(selectedDestination == nil)` (`:285`) becomes the adapter's `validate` result
- [ ] `TaskStore.parsedDraft` (`Store/TaskStore.swift:68-91`) assembles the bag rather than three fixed
      properties; the private `TaskDueDateOverride` enum generalises to per-field overrides

### 3.1 The registry is injectable, not a `switch`

If mapping value types to editors stays a `switch` inside the composer, then "add a component" means editing
composer code every time — the thing this release exists to prevent. It is a registry keyed on **value type**,
with an optional override keyed on **field ID**, so Reminders' `.location` can claim a map picker while a
generic geo field elsewhere still falls back to something sane.

### 3.2 Editor state lives in the draft, not the editor view

`DrawerContentHost` applies `.id(route)` (`Views/DrawerMotion.swift:96`), so changing route tears the view down
and rebuilds it. Today that is invisible — the date presets are stateless. With a stateful editor it is a
visible regression: tab to another chip and back, and an in-progress place search or scroll position is gone.

This is a design consequence rather than a bug, and it reinforces the keyed-dictionary shape: **the draft owns
field state, editors are projections of it.**

### 3.3 Precedent

`DateChooser` is already a complex field editor that manages its own internal navigation — it nests a private
`DrawerState<DatePage>` to go presets → calendar (`:339`, `:407-410`) and the host knows nothing about it. Any
future editor nests the same way. The pattern is proven in-tree, not hypothetical.

## 4. The display side

- [ ] `TaskRowView`'s metadata line (`Views/TaskRowView.swift:39-53`) is hardcoded to due date + context. It
      becomes: render `dueDate` richly as it does now, then the field bag as labelled chips.

A Jira task returning title + project + sprint + priority renders with no Jira-specific view code, because
priority is a `.choice` whose selected option carries its own display name.

**Grouping stays on the due-date axis.** `TaskSection` (`Models/TaskItem.swift:50-89`) is a fixed five-case
date axis, and the original concern was that issue-tracker tasks would all fall into "Unscheduled". Resolved as
**not a problem** — Jira issues carry real due dates, so the existing axis holds and status/sprint/priority ride
along as displayed metadata. Source-declared or user-selectable grouping axes are a someday-maybe, not 0.2.

## 5. Opening the closed shapes

Each of these costs a core-file edit per integration today.

| Site | Change |
|---|---|
| `Models/TaskSource.swift:3-13` | **Delete `TaskSourceCapabilities`.** |
| `Models/TaskSource.swift:27-41` | Static `.markdown` / `.reminders` descriptors → a registry of adapters |
| `Store/TaskStore.swift:29` | `let sources: [TaskSourceDescriptor]` is a hardcoded array of the same |
| `Models/TaskItem.swift:40-48` | `TaskSourceLocation` — closed enum, `case markdown(…)` → opaque token |
| `Models/TaskItem.swift:5-12` | Fixed `note` / `context`; nowhere for sprint or priority |
| `Services/TaskDraftParser.swift:3-7` | `TaskDraft` — three fixed stored properties |

`TaskSourceCapabilities` deserves its own note: it is **this release's idea already in the codebase, in the
wrong shape.** `.dueDates`, `.notes`, `.tags`, `.locations` *is* a field schema, expressed as a closed bitmask
in a core file that every integration must edit. It is read by **zero call sites** outside its own declaration,
and it is already lying — Markdown declares `.notes` and `.tags` and populates neither. It dies into `TaskField`.

## 6. Settings extensibility

`Views/SettingsView.swift` is more hardcoded to Markdown than the composer is. Three separate methods branch on
`source.id == markdown`:

- `isUsable` (`:60-64`) — "usable" means `markdownFolderURL != nil`
- `trailingControl` (`:115-127`) — the "Choose Folder…" button, written inline
- `subtitle` (`:148-158`) — per-source copy, with the Reminders string hardcoded as a placeholder

As it stands, connecting *any* second source means editing all three. Adapters declare their own setup
affordance — a label, a current-state summary, and an async action — and the pane renders it.

- [ ] Setup affordance on the adapter; `SourcesSettingsPane` loses all three Markdown branches
- [ ] The `.reminders` descriptor with `availability: .planned` is a UI fiction with no adapter behind it.
      Either back it with a real registry entry or drop it until the adapter exists.

**A new connector shipping its own Settings UI is accepted and fine.** The goal is that it *may*, not that it
*must*.

## 7. Validation

- [ ] `TaskFieldIssue` — per-field complaints from the adapter
- [ ] Add enables on `validate` returning empty, not on `selectedDestination != nil`
- [ ] Chips mark themselves when their field has an issue

Jira will demand a non-empty assignee. That check cannot live in a view.

## Appendix: the worst case, walked through

The design was pressure-tested against the hardest thing 0.3+ might ask for: **Apple Reminders as a new
connector, and a map picker as a new UI component, at the same time.**

**Free** — routing (the map is just another `TaskFieldID` route), the reveal/forward/backward animation, the
divider, the clipping, the chip, validation, persistence, and the whole create path. `DrawerMotion.swift` needs
zero changes.

**Actually written** — one `TaskFieldValue` case, one editor view, one registry entry, and the EventKit adapter
(which is the bulk of the work and has nothing to do with any of this).

The one honest cost is that case: a coordinate pair is not text, number, date or choice, so the closed enum
grows and that is a core-file edit. But the ratio is the design working, not failing — **value types grow with
kinds of data; integrations grow with services.** Jira, SIM, Linear and Todoist add zero new value types between
them. Reminders adds one, once.

**Genuinely hard, and none of it architectural** — MapKit gestures inside a `MenuBarExtra(.window)` panel that
dismisses on outside click; CoreLocation authorization from an `LSUIElement` process (the same class of problem
as Settings opening behind everything, fixed at `MenuBarContentView.swift:168`); sandbox entitlements and
`NSRemindersFullAccessUsageDescription`; and a height budget — the window is a fixed 536×548 (`:93`), so after
the 44pt header, 40pt chip bar and 42pt footer there is ~420pt to split between drawer and task list, and a map
with a search field wants ~320 of it. Nothing in the app has yet rendered a drawer taller than ~180pt.

That the expensive parts are all platform work rather than framework work is the reason this design was
accepted.

## Explicitly not in 0.2

- **Any real integration.** No Jira, no SIM, no Reminders, no Linear. Shapes only.
- **Networking.** No entitlement, no auth, no token storage — that lands with the first remote adapter.
- **The fail-fast fetch loop.** `TaskStore.reloadTasks` (`Store/TaskStore.swift:258-279`) returns on the first
  error, discarding every healthy source's tasks. A real bug that matters the moment there are two sources — but
  a store fix, not a shape fix. First item in the release that adds a second adapter.
- **Alternate grouping axes** — see §4.
- **Per-source error copy.** `.operationFailed` still shows raw `error.localizedDescription`; carried over from
  0.1 §1.2 and still waiting on a real second source to design against.
- **Source-defined task status.** 0.1 §4.2 settled `x`/`X`/`-` as resolved and everything else as open. Real
  multi-state status (Jira's workflow states) needs the field model to exist first, and then its own design pass.
- **Editing existing tasks.** The field model makes it plausible; the app still has no edit affordance at all.

Still out from 0.1 and unchanged: global hotkey · keyboard list navigation · ⌘Z undo · notarization · Sparkle ·
localization · incremental parse cache.
